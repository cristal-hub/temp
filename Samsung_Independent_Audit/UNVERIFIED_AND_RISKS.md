## A. Неподтверждённые / опровергнутые утверждения предыдущих отчётов

### U-1. Утверждение «runtime-файлы побайтово идентичны Samsung 051b10f» — ОПРОВЕРГНУТО для BUY-кандидата

* Источник утверждения: `Samsung_BUY_Accounting_Audit_V1/CHANGED_FILES.md`, §4
  «Файлы, НЕ изменённые (сверка SHA256 с Samsung 051b10f)»: перечислены
  `state.json`, `order_ledger.jsonl`, `research_trades.csv`,
  `research_events.jsonl`, `sandbox_pnl.csv` как «побайтово идентичны».
  Аналогичное утверждение содержится в унаследованном `KNOWN_LIMITATIONS.md` §4.
* Фактические SHA256 (установлены независимо):
  * `state.json`: baseline/B2 = `78a9eeb8…` (5353 байта); **BUY = `44c9f9ab…`
    (169 байт) — СБРОШЕН**. Содержимое BUY-версии: пустые `positions`,
    `closed_entry_order_ids: []`, `pending_csv_recoveries: []`,
    `open_orders: []`, `risk: {"fake": true}` — то есть тестовая заглушка,
    прямо помеченная `"fake": true`.
  * `research_events.jsonl`: baseline/B2 = `f8a8acbc…` (18329 байт, 46 событий);
    **BUY = `0aaa9431…` (54427 байт, 206 событий)** — 160 событий, добавленных
    тестовыми прогонами (фиктивные FIGI `F1`, тикер `T`, синтетический MVID,
    `TRADING_START`/`TRADING_STOP`, `STATE_SAVE_FAILED`, `RECONCILE_MISMATCH`).
* Почему это важно:
  1. ТЗ аудита прямо запрещает изменение реальных `state.json` /
     `research_events.jsonl`. BUY-пакет содержит изменённые копии обоих.
  2. Реальные артефакты инцидентной LSRG-позиции (CLOSED-запись,
     `open_orders` с заявками 495f583f/46386d0c, `closed_entry_order_ids`),
     присутствовавшие в state.json baseline/B2, из BUY-пакета **удалены** —
     вещественная доказательная база инцидента из пакета утрачена (сохранилась
     в baseline/B2 и в order_ledger.jsonl, который общий для всех трёх).
  3. Само утверждение отчёта кандидата ложно — это документальный дефект
     пакета, подрывающий доверие к остальным заявлениям, пока они не сверены
     независимо (в рамках настоящего аудита остальные ключевые заявления
     сверены — см. VERIFIED_CHANGES.md).
* Критичность: **ВЫСОКАЯ для достоверности пакета** (не для runtime-кода:
  в проде файл будет создан заново при первом сохранении состояния).
* Для исправления: восстановить в пакете state.json и research_events.jsonl
  байт-в-байт из baseline 051b10f (или пометить файлы как изменённые в
  CHANGED_FILES.md), тесты запускать во временной копии с перенаправлением
  рабочего каталога.

### U-2. «Прогоны pytest не изменяли runtime-файлы» — ОПРОВЕРГНУТО (причина U-1)

* Тесты пишут `research_events.jsonl`/`research_trades.csv`/`state.json` в
  текущий рабочий каталог (logger.py: `TRADES_FILE = "research_trades.csv"`,
  `EVENTS_FILE = "research_events.jsonl"`; state — `_save_state`). Часть тестов
  перенаправляет файлы в tmp_path, но НЕ все (например, тесты BUY-аудита
  используют tmp_path; при запуске из корня кандидата часть событий всё же
  записывается в реальный журнал — 160 добавленных событий в U-1 тому
  доказательство).
* Тесты можно запускать безопасно только в отдельной копии каталога (как
  сделано в настоящем аудите). Прямое указание в отчёте кандидата
  (`run_tests.ps1`, README) запускает pytest из корня пакета — воспроизводит
  загрязнение.
* Критичность: СРЕДНЯЯ (гигиена артефактов; риск повторного «тихого» изменения
  runtime-файлов при следующих интеграциях).

### U-3. Заявления отчётов P0-4/P0-5/Stage-3 «265/269/341 passed» — НЕ ВОСПРОИЗВОДИМЫ на текущем baseline

* `ОТЧЁТ_P0-5.md`: «Полный набор ПОСЛЕ правок P0-5 — 269 passed, 0 failed»;
  `РЕЗУЛЬТАТЫ_ТЕСТОВ_P0-4.txt`: «265 passed»;
  `ОТЧЁТ_ЭТАП3_SAFETY_FIX_SELL.md`: «341 passed» (tests/).
* Фактически (независимые прогоны на baseline 051b10f, B2 и BUY — см.
  TEST_RESULTS.md): `tests/` = 49 failed / 249 passed; полный сбор = 74 failed
  / 1 collection error. Набор падений ИДЕНТИЧЕН во всех трёх деревьях и,
  следовательно, возник до контрольного коммита (ЭТАП 5Б добавил kwarg
  `order_id_type` в вызовы `get_sandbox_order_state`, а старые FakeClient-заглушки
  в `test_p0_batch2_late_execution.py`, `tests/test_p0_defect_fixes.py` и др.
  не обновлялись).
* Вывод: заявления верны для своих коммитов времени выполнения, но в
  поставляемом состоянии (baseline 051b10f → B2 → BUY) обязательные тесты
  P0-3/P0-4 (включая `test_p03_1..3`, `test_p04_*`) и P0-5 (`test_p05_1..4`)
  **не проходят** — сквозная тестовая верификация P0-батчей на текущем коде
  ОТСУТСТВУЕТ (покрытие частично замещается B2 v1–v7 (96/96) и BUY-тестами
  (23/23), которые соседние пути закрывают).
* Критичность: ВЫСОКАЯ как дыра верификации; СРЕДНЯЯ как риск кода (падения —
  устаревшие заглушки, не производственный код; точный состав в
  REGRESSION_COMPARISON.md).
* Для исправления: отдельное ТЗ на обновление устаревших заглушек
  (`order_id_type` в FakeClient), без изменения production-кода и без удаления
  тестов.

### U-5. Семантика `executed_order_price` — подтверждена только на заглушках

* `ExecutionMonitor._extract_price` делит кумулятивную денежную сумму исполнения
  на `lots_executed * lot_size`. Соответствие этому контракту реального SDK
  (t-tech-investments 1.51.0) в песочнице проверялось только авторами на
  заглушках; в среде настоящего аудита SDK отсутствует — НЕ воспроизведено.
* Риск: если бы поле было не кумулятивным, средняя цена исполнения во всех
  расчётах была бы неверной. Отнесено кандидатом к «Потенциальным» (AUDIT_REPORT §8,
  п.5); настоящий аудит согласен с классификацией.
* Для снятия риска: разовая проверка на реальном sandbox-отчёте (READ-ONLY,
  без заявок) — отдельно от этого аудита.

### U-6. «Ни один тест не удалён» — ПОДТВЕРЖДЕНО, с одной оговоркой

* Поимённое сравнение тестов baseline → B2 → BUY: удалений нет; обновлён один
  тест-контракт (`test_extract_commission_zero_returns_none` →
  `_zero_returns_zero`, семантика FIX-3, документировано, покрытие не ослаблено —

* Оговорка: корневой `test_execution.py` не выполняется НИ в одном прогоне

  присутствует, но фактически исключён из прогона. Это существовало в baseline
  и не создано кандидатами.

## B. Оставшиеся риски (зафиксированы, не исправлялись)

### R-1. FIX-3 затрагивает общую функцию — SELL-путь B2 в частном случае меняет поведение

* `_extract_commission()` используется и `resolve_closing()` (SELL-закрытие B2).
  При РЕАЛЬНО нулевой комиссии закрытия раньше в cursor записывался None
  (→ модельная комиссия в P&L), теперь — 0.0 (→ фактическая нулевая).
* Оценка: изменение направлено на точность учёта и явно документировано
  кандидатом (комментарий FIX-3), но формально это первое изменение B2-семантики
  SELL-пути со стороны BUY-аудита. B2 v1–v7 тесты (96/96) проходят; отдельного
  теста «SELL-комиссия = 0» в наборе нет.
* Риск: НИЗКИЙ (вероятность нулевой комиссии у брокера мала), но требуется
  осознанное принятие.
* Для исправления (при желании): добaвить тест на нулевую комиссию SELL-закрытия
  в B2-набор (без изменения production).

### R-2. FIX-1 применяется ко ВСЕМ записям реестра, включая SELL

* Защита повторного отчёта (identity/цена/комиссия, UNCERTAIN при конфликте)
  добавлена в общий `append()` — она распространяется и на SELL-записи B2.
  Направление fail-closed; при консистентных отчётах поведение не меняется.
  B2-тесты проходят. Риск: НИЗКИЙ.

### R-3. Нет операторских команд разрешения неопределённостей

* Telegram-бот имеет только /start, /stop, /status. Состояния UNCERTAIN-позиции,
  «зависший» INTENT в реестре, `ledger.is_reliable()=False`, `state_save_failed`
  разрешаются ТОЛЬКО терминальными отчётами брокера либо ручными процедурами
  оператора (правки файлов/рестарт), описанными в комментариях кода, но не
  оформленными как инструмент. Позиция не может быть заблокирована «навсегда»
  при работающем брокере (опрос продолжается), но при недоступности брокера
  блокировка сохраняется до вмешательства.
* Риск: СРЕДНИЙ (операционный), направление fail-closed — осознанное.
  Предсуществовало (baseline), кандидатами не усугублено.

### R-4. 74 предсуществующих падения тестов не устранены

* Полный набор падает одинаково в baseline, B2 и BUY (74 FAILED + 1 collection
  error; имена идентичны до теста — см. REGRESSION_COMPARISON.md). Состав:
  устаревшие заглушки `order_id_type` (~34), заглушка pandas_ta_classic без
  `adx` (6), screener без SDK (12), persistence-subprocess (4),
  `tests/test_main_helpers.py` PRICE_UNKNOWN/commission_source «none» vs
  «model» (6), прочие. Покрытие сценариев этих тестов фактически потеряно до
  исправления заглушек.
* Критичность: ВЫСОКАЯ как дыра верификации; производственный код не показан
  дефектным ни одним из этих падений (все — расхождения тест-стабов/среды).

### R-5. `sandbox_topup.py` содержит захардкоженный ACCOUNT_ID

* Предсуществовало; счёт песочницы (`538f670d-…`). Секретов (токенов) в пакете
  НЕТ — токены читаются из `.env` (проверено: `config.py` читает os.getenv;
  `.env` в пакет не входит). Риск: НИЗКИЙ (утечка несущественна для sandbox,
  но захардкоженный ID — плохая практика).

### R-6. Повторный вход через 2 секунды после LEDGER_CLOSE (наблюдение из артефактов)

* В артефактах baseline/B2 (research_events.jsonl) зафиксирован эпизод: LSRG,
  SELL подтверждена реестром (LEDGER_CLOSE) в 10:40:01, новый SIGNAL/BUY в
  10:40:03. Учёт корректен (обе сделки закрыты, дубликатов P&L нет), но
  интервал перепроверки ликвидности позиции брокером в момент нового BUY
  определяется снимком портфеля шага 6; при задержке маппинга сделок брокером
  возможен вход на позицию, которая у брокера ещё числится. Существующие
  защиты: `figi_blocks_buy` по реестру, наличие активной позиции в памяти,
  reconcile. Это наблюдение из истории, НЕ дефект кандидата; рекомендуется
  учесть при отдельном исследовании частоты RECONCILE_MISMATCH (в тестовых
  событиях кандидата такие есть — 8 шт., из тестов).

### R-7. Незавершённое разрешение «крах до record_intent» (окно RC-2)

* Единственное окно, в котором BUY-заявка не оставляет следа в реестре
  (признано кандидатом, ROOT_CAUSE_ANALYSIS RC-2): позиция обнаруживается
  только адопцией reconcile/startup как RECOVERY. Механизм адопции работает
  (тесты ТЗ-14/15), но entry_order_id/цена в этой позиции неизвестны до
  привязки. Риск: НИЗКИЙ-СРЕДНИЙ; полностью устранить нельзя (крах до INTENT
  по определению безследен), смягчено адопцией.
