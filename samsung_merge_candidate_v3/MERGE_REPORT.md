## 4. Что было исправлено (детально)

### 4.1 Дефект

`process_closing()` записывает CSV-строку один раз: после успешного
`log_trade` позиция получает `pos.logged=True` и больше никогда не
рассматривается циклом записи. Типовые сценарии ТЗ:

- **A**: цена известна, фактической комиссии нет → в CSV расчётная
  (модельная) комиссия; позднее приходит фактическая — CSV не обновлялся.
- **B**: цена неизвестна → CSV с PRICE_UNKNOWN и пустыми финансовыми
  полями; позднее приходит фактическая цена — CSV не обновлялся.
- **C**: цена и комиссия приходят в разное время — CSV не обновлялся.

Причины: (1) для CLOSED+logged позиций не существовало пути опроса
брокера — `resolve_closing` вызывается только для CLOSING/UNCERTAIN,
`reconcile` — только для ACTIVE_STATES; (2) не существовало механизма
обновления записанной строки — `log_trade` append-only.

### 4.2 Реализация (main.py + logger.py; execution.py НЕ изменялся)

**logger.py (новые функции)**:
- `find_trade_row(trade_id)` — поиск ЕДИНСТВЕННОЙ строки по стабильному
  trade_id (missing/ambiguous → отказ, fail-closed);
- `update_trade_row(trade_id, updates)` — обновление СУЩЕСТВУЮЩЕЙ строки:
  перезапись столбца trade_id запрещена; применение обновлений без
  изменения ни одной строки не переписывает файл (идемпотентность);
  после применения — пересчёт `cumulative_net_pnl_rub` ВСЕХ строк в
  порядке файла; АТОМАРНАЯ запись (см. 4.4);
- `_write_all_trade_rows_atomic` — временный файл в той же директории
  (`mkstemp`) + flush + fsync + ПРОВЕРКА результата (перечитать temp:
  шапка и число строк совпадают) + `os.replace` + fsync директории;
  при любой ошибке temp удаляется, исходный файл не изменяется;
- `_recompute_cumulative` — накопительный P&L последующих сделок
  пересчитывается в хронологическом порядке; строки PRICE_UNKNOWN
  (пустой net) не меняются и в сумму не входят; детерминирован.

**main.py (новые функции + интеграция)**:
- recovery-проход в конце `process_closing` по CLOSED+logged позициям —
  `pos.logged=True` больше НЕ блокирует обновление записанной сделки;
- `_recover_late_csv_metadata(client, pos)`:
  1. найти строку по стабильному trade_id (нет/неоднозначен → отказ);
  2. определить, есть ли что восстанавливать: exit_price или
     actual_commission_rub в строке пусты (иначе — выход, опросов нет);
  3. опросить отчёт брокера по close-заявке (биржевой ID → EXCHANGE,
     клиентский UUID → REQUEST — та же семантика, что `resolve_closing`);
  4. сверить отчёт с замороженным терминальным cursor'ом: канонический
     статус совпадает, cumulative совпадает, цена/комиссия без конфликта
     (`_confirmed_value_conflicts` — конфликт только при двух достоверных
     разных значениях); любое расхождение → fail-closed БЕЗ изменений,
     событие `CSV_LATE_METADATA_CONFLICT`;
  5. безопасное обогащение ТОЛЬКО отсутствующих значений cursor'а
     (семантика v2.3.5) + синхронизация pos.execution_price /
     pos.exit_price_confirmed / pos.actual_commission; событие
     `CSV_LATE_METADATA_ENRICHED`;
  6. пересчитать зависимые поля (`_build_late_recovery_updates`) и
     атомарно обновить строку (`update_trade_row`); событие
     `CSV_TRADE_ROW_UPDATED` со списком изменённых полей.
- `_build_late_recovery_updates` — формулы и форматы ИДЕНТИЧНЫ штатной
  записи CSV: gross/net P&L, комиссия (фактическая; модельная только при
  отсутствии фактической), commission_source actual/mixed/model,
  проскальзывание; лоты берутся из СУЩЕСТВУЮЩЕЙ строки и не меняются;
  PRICE_UNKNOWN-маркер удаляется при подтверждении цены; для строки с
  неподтверждённой ценой обновляется только факт комиссии (P&L не
  изобретается).

### 4.3 Почему потребовалось изменение именно этих файлов

- **logger.py** — единственный владелец записи research_trades.csv
  (`log_trade`); любой корректный механизм обновления строки обязан
  гарантировать атомарность и целостность остального файла — это функция
  уровня журнала, а не main.py.
- **main.py** — владелец жизненного цикла process_closing (где известны
  клиент, позиция, cursor и контекст закрытия) и уже содержит
  валидированную логику сверки повторных отчётов
  (`_confirmed_value_conflicts`, `_canonical_report_status`,
  `_SELL_JOURNAL_TERMINAL_STATUSES`), которую recovery обязан применять
  согласованно с B2.
- **execution.py НЕ потребовался**: v2.3.5-stage1 уже решает обогащение
  cursor'а для позиций, проходящих через `apply_close_execution`; для
  CLOSED+logged позиций вызывать этот метод НЕЛЬЗЯ без побочных эффектов
  (ветки конфликта переводят позицию в UNCERTAIN — недопустимый churn для
  закрытой учётной единицы). Recovery реализует обогащение по той же
  семантике на уровне main.py без вызова state-меняющих веток.

### 4.4 Идемпотентность и целостность CSV

- **Повторный одинаковый отчёт не меняет результат второй раз**: enrichment
  добавляет только отсутствующие значения; построенные обновления
  сравниваются с текущим содержимым строки; `update_trade_row` возвращает
  "unchanged" и НЕ переписывает файл, если ни одна строка (включая
  пересчёт cumulative) не изменилась (тесты E, H, N — файл байт-в-байт).
- **Повторный запуск после перезапуска не создаёт дублей**: обновляется
  СУЩЕСТВУЮЩАЯ строка; новых строк механизм не создаёт никогда; штатная
  защита `_trade_id_already_logged` сохранена (тесты F, H, M).
- **Атомарность**: сбой на ЛЮБОМ шаге (запись, fsync, проверка, replace)
  оставляет исходный файл нетронутым, temp удаляется (тест L; исходный
  файл сверяется байт-в-байт, временные файлы не остаются).
- **Один trade_id → одна строка**: 0 или >1 совпадений → отказ (тест M).
- **Остальные строки не повреждаются**: перезаписывается полный набор
  строк из проверенного чтения; тест G проверяет, что net_pnl_rub строк
  t2/t3 не изменился, изменился только их cumulative.

### 4.5 Решение по состоянию позиции при конфликте (обоснование)

При противоречивом позднем отчёте для CLOSED+logged позиции конфликт
фиксируется (лог ERROR + событие `CSV_LATE_METADATA_CONFLICT`), но позиция
НЕ переводится в UNCERTAIN (в отличие от активных позиций в
`apply_close_execution`). Обоснование: (1) учёт уже закрыт, количество не
меняется — противоречие касается ТОЛЬКО метаданных; (2) возврат CLOSED→UNCERTAIN
запускал бы повторное разрешение через resolve_uncertain/B3 (churn
учётного состояния, риск ложного EXTERNAL_CLOSE-переоформления); (3)
fail-closed по существу: ни одно значение не перезаписывается, ни одна
строка не изменяется, конфликт доказуемо зарегистрирован. Лот-уровневые
противоречия (рост cumulative после терминала) по-прежнему обрабатываются
жёстким fail-closed в `apply_close_execution` — эти ветки не затронуты.

## 5. Как восстанавливаются цена/комиссия (сквозной сценарий)

1. Позиция закрыта своим close-ордером; отчёт при терминале не содержал
   цены и/или комиссии → cursor хранит None; CSV-строка записана штатно
   (PRICE_UNKNOWN с пустыми финансовыми полями и/или модельная комиссия).
2. Поздний отчёт брокера (следующие циклы process_closing) содержит
   подтверждённую цену и/или комиссию → recovery сверяет с cursor'ом →
   отсутствующие значения записываются в cursor и синхронизируются в
   позицию (semantics v2.3.5) → событие CSV_LATE_METADATA_ENRICHED.
3. `_build_late_recovery_updates` пересчитывает зависимые поля по формулам
   штатной записи; `update_trade_row` атомарно обновляет строку и
   пересчитывает накопительный P&L последующих сделок → CSV_TRADE_ROW_UPDATED.
4. Опрос продолжается только пока в строке есть пустые
   exit_price/actual_commission_rub; после подтверждения обоих значений
   позиция больше не опрашивается.

Ограничения семантики (по ТЗ): фактическая комиссия не подменяется
расчётной (модельная используется только при ОТСУТСТВИИ фактической);
известная цена/комиссия не перезаписываются противоречивыми значениями;
отсутствие данных не трактуется как ноль.

## 7. Ограничения и известные проблемы (без маскировки)

1. **Мультиордерные закрытия**: recovery обрабатывает close-заявку, на
   которую указывают ссылки позиции (`close_order_request_id` /
   `close_order_id` — та же заявка, что в столбце order_id CSV-строки).
   Cursor'ы ПРЕДЫДУЩИХ SELL-заявок той же позиции обогащаются только
   механизмом v2.3.5 (повторные отчёты через apply_close_execution для
   ещё-не-CLOSED позиций). Не менялось: предсуществующая семантика
   pos.executed_lots/cumulative последней заявки — исправление требует
   пересмотра формул P&L по совокупности заявок (вне рамок этапа).
2. **Позиции без trade_id**: строка, записанная по случайному
   идентификатору, надёжно не идентифицируется — обновление запрещено
   (fail-closed, ТЗ M); в журнале — debug-сообщение. Восстановление для
   таких сделок невозможно без расширения схемы state.json (не проводилось:
   «не менять схему без обоснованной необходимости»).
3. **B3-внешние закрытия** (без своей SELL-заявки): ссылок на close-заявку
   нет → опрос невозможен, строка остаётся PRICE_UNKNOWN по дизайну
   (price_confirmed=False запрещает фиктивный P&L). B3 не менялся.
4. **Накопительный P&L после восстановления**: пересчитывается из строк
   CSV (значения, округлённые до 0.01). Расхождение с исходной арифметикой
   writer'а (writer прибавлял неокруглённый net текущей строки) ≤ 0.005 на
   строку; метод детерминирован и повторяем.
5. **Опрос CLOSED+logged позиций**: выполняется каждый цикл для позиций с
   неполными данными и завершается сам после подтверждения обоих значений;
   для позиций, у которых брокер не передаёт комиссию в отчёте заявки,
   опрос продолжается (как и для UNCERTAIN-позиций в B2-пути v2.3.4 —
   «неизвестная комиссия — самостоятельное основание для запроса отчёта»).
6. **Полные строки не опрашиваются**: если цена И фактическая комиссия уже
   в CSV, противоречивый поздний отчёт не проверяется (нет опроса → нет
   изменений → fail-closed по существу); диагностика таких отчётов
   ограничена. Осознанный компромисс против бесконечного опроса всех
   закрытых позиций.
7. **Схема CSV и state.json не расширялись**; `csv_trade_id`-подобные
   поля не добавлялись (см. п. 2).
