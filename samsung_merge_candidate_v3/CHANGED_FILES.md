## Детализация изменений и обоснование каждого

### 1. main.py — `_recover_late_csv_metadata(client, pos)` (НОВОЕ)

**Что**: для CLOSED+logged позиций с неполными подтверждёнными данными —
поиск исходной строки по стабильному trade_id, опрос отчёта брокера по
close-заявке (семантика идентификаторов как в `resolve_closing`: биржевой
ID → EXCHANGE, клиентский UUID → REQUEST), сверка отчёта с замороженным
терминальным состоянием per-order cursor'а, безопасное обогащение
отсутствующих значений, атомарное обновление существующей CSV-строки.

**Обоснование**: единственный способ устранить расхождение CSV и
оперативного учёта. Ранее для CLOSED+logged позиций не существовало ни
одного пути опроса брокера (`resolve_closing` вызывается только для
CLOSING/UNCERTAIN, `reconcile` — только для ACTIVE_STATES) и ни одного
механизма исправления записанной строки (`log_trade` — append-only).

**Ограничения, встроенные в функцию**:
- лоты не применяются повторно (функция не вызывает `apply_close_execution`;
  applied/confirmed/quantity/close_applications не изменяются);
- отчёт сверяется с cursor'ом: тот же канонический терминальный статус,
  то же cumulative; цена/комиссия — через `_confirmed_value_conflicts`;
  любое расхождение — fail-closed БЕЗ изменений (событие
  `CSV_LATE_METADATA_CONFLICT`);
- CLOSED-позиция не переворачивается в UNCERTAIN при конфликте метаданных:
  повторное разрешение через B3 порождало бы churn учётного состояния;
  конфликт фиксируется журналом и событием (обоснование см. MERGE_REPORT §5);
- безопасное обогащение — ТОЛЬКО отсутствующие значения cursor'а
  (семантика v2.3.5-stage1); известные не перезаписываются; отсутствие
  значения в новом отчёте — не противоречие;
- отсутствующий/неоднозначный trade_id — обновление запрещено.

### 2. main.py — `_build_late_recovery_updates(pos, old_row)` (НОВОЕ)

**Что**: пересчёт зависимых финансовых полей CSV по текущим подтверждённым
данным позиции. Формулы и денежные форматы идентичны штатной записи CSV
(v2.3.1-stage1): gross/net P&L, комиссия (фактическая; модельная — только
при ОТСУТСТВИИ фактической), `commission_source` = actual/mixed/model,
проскальзывание. Возвращает ТОЛЬКО изменившиеся поля.

**Обоснование**: при позднем подтверждении цены/комиссии зависимые поля
(включая net P&L и накопительный итог) должны быть пересчитаны из
достоверных исходных данных. Количество исполненных лотов берётся из
СУЩЕСТВУЮЩЕЙ строки и не меняется. Для строки с неподтверждённой ценой
обновляется только ФАКТ фактической комиссии (не зависит от цены); P&L не
изобретается (запрет фиктивного P&L сохранён).

### 3. main.py — recovery-проход в `process_closing` (ДОБАВЛЕНИЕ)

**Что**: после штатного цикла записи CSV — цикл по CLOSED+logged позициям
с вызовом `_recover_late_csv_metadata` в try/except (сбой восстановления
не влияет на учёт).

**Обоснование**: ТЗ «Не допускать ситуации, когда pos.logged=True
препятствует необходимому обновлению уже записанной сделки».

### 4. main.py — константа `_CSV_PRICE_UNKNOWN_MARKER` (ДОБАВЛЕНИЕ)

**Что**: литерал маркера вынесен в константу; writer и механизм удаления
маркера (`_remove_price_unknown_marker`) используют один источник строки.

**Обоснование**: исключение расхождения строк маркера между записью и
удалением; удаление маркера — требование ТЗ («убрать PRICE_UNKNOWN, когда
цена действительно подтверждена»). Остальные пометки error_note
(например, «частичное исполнение SELL (3/10)») сохраняются.

### 5. logger.py — `find_trade_row(trade_id)` (НОВОЕ)

**Что**: поиск ЕДИНСТВЕННОЙ строки по trade_id; статусы found/missing/
ambiguous/error. Неоднозначный (дублирующийся) trade_id → отказ.

**Обоснование**: ТЗ «найти исходную сделку по стабильному trade_id» +
«отсутствующий или неоднозначный trade_id не приводит к обновлению чужой
сделки» (тест M).

### 6. logger.py — `update_trade_row(trade_id, updates)` (НОВОЕ)

**Что**: точечное обновление существующей строки CSV: перезапись столбца
`trade_id` запрещена; идемпотентность (нет изменений — файл не
переписывается); пересчёт накопительного P&L всех строк в порядке файла
(`_recompute_cumulative`); АТОМАРНАЯ запись (`_write_all_trade_rows_atomic`).

**Обоснование**: ТЗ раздел 3 (обновить существующую строку, не создавать
новую; сохранить trade_id; пересчитать накопительный P&L последующих сделок
в правильном временном порядке) и раздел 4 (целостность CSV).

### 7. logger.py — `_write_all_trade_rows_atomic(rows, fieldnames, expect_rows)` (НОВОЕ)

**Что**: полный набор строк пишется во временный файл в той же директории
(`tempfile.mkstemp`), flush + fsync, закрытие, ПРОВЕРКА результата
(перечитать временный файл: шапка и число строк данных совпадают с
исходными), затем `os.replace` (атомарная подмена) + fsync директории
(best-effort). При любой ошибке на любом шаге временный файл удаляется,
исходный файл не изменяется. Обрезанные/битые строки нормализуются
(недостающие поля — пустые, лишние столбцы отбрасываются с warning) —
данные строк не теряются, схема CSV не меняется.

**Обоснование**: ТЗ «Предпочтительно использовать безопасную атомарную
запись через временный файл с проверкой результата»; «если обновление CSV
прервано, исходный файл должен оставаться целостным» (тест L).

### 8. logger.py — `_recompute_cumulative(rows)` (НОВОЕ)

**Что**: пересчёт `cumulative_net_pnl_rub` для всех строк с непустым
`net_pnl_rub` в порядке файла (= хронологическом порядке закрытий); строки
PRICE_UNKNOWN (пустой net) не меняются и в сумму не входят. Детерминирован:
значения парсятся из строк CSV — повторный запуск даёт тот же результат.

**Обоснование**: ТЗ «пересчитать накопительный P&L для последующих сделок в
правильном временном порядке» (тест G). Разница с исходной арифметикой
writer'а (writer прибавлял неокруглённый net текущей строки) ≤ 0.005 на
строку — задокументировано в MERGE_REPORT §7.

### 9. execution.py — БЕЗ ИЗМЕНЕНИЙ

Механизм v2.3.5-stage1 (безопасное обогащение терминального повтора в
`apply_close_execution`) полностью достаточен: recovery-путь main.py
переиспользует его СЕМАНТИКУ, но не вызывает сам метод (CLOSED-позиция не
должна проходить через ветки смены состояния). B3 (`_finalize_position_closed`,
`resolve_uncertain`, двойное подтверждение) — байт-идентично v2/v1.
