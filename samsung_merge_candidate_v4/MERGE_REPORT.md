## 1. Краткий результат

Закрыты два дефекта B2-учёта, обнаруженных после v3:

**Дефект №1 — накопительный P&L не гарантированно хронологический.**
`_recompute_cumulative` (v3) суммировал строки в ПОРЯДКЕ ФАЙЛА, а порядок
строк CSV — это порядок ЗАПИСИ (порядок обхода `monitor.positions` =
порядок регистрации позиций; момент записи каждой строки). Он не
гарантирует хронологию ФАКТИЧЕСКИХ закрытий: позиции могут
регистрироваться в одном порядке, а закрываться в другом; при
логировании нескольких закрытий в одном цикле порядок строк =
регистрационный, а не временной; позднее восстановление метаданных
старой сделки меняет её net P&L и требует пересчёта всех последующих
сделок именно в ХРОНОЛОГИЧЕСКОМ порядке. Дополнительно столбец
`exit_time` заполнялся моментом записи строки (`now()`), т.е. вообще
не нёс информацию о фактическом времени закрытия.

**Дефект №2 — незавершённое восстановление терялось при новой позиции
по тому же FIGI.** Recovery-цикл v3 обходил `monitor.positions.values()`.
`monitor.register()` / `register_recovery()` ЗАМЕНЯЮТ объект в
`positions[figi]` (закрытая позиция вытесняется) — прежняя сделка
переставала попадать в recovery-цикл, поздний отчёт брокера больше
не доходил до её CSV-строки. То же происходило и после перезапуска:
новая позиция того же FIGI вытесняла восстановленную из state.json
закрытую позицию. Единственным источником recovery-задач была
оперативная структура `positions[figi]` — нарушение главного принципа:
одна фактическая сделка должна сохранять идентичность и корректный
финансовый учёт независимо от порядка закрытия других сделок,
появления новой позиции по тому же FIGI и перезапуска программы.

Реализация v2.3.7-stage1:
- **logger.py**: пересчёт cumulative в ГАРАНТИРОВАННОМ хронологическом
  порядке (авторитетное время — `exit_time`, детерминированная
  fallback-цепочка, tie-breaker — `trade_id` + индекс строки);
  канонизация журнала после каждой записи (`log_trade`);
- **main.py**: `exit_time` пишется как время ЗАПРОСА закрытия
  (`close_requested_at`), а не момент записи строки; recovery-проход
  по ПЕРСИСТЕНТНОМУ архиву незавершённых задач;
- **execution.py**: архив незавершённых recovery-задач
  (`pending_csv_recoveries`) — снимки закрытых сделок, сохраняемые
  ПЕРЕД заменой позиции по тому же FIGI и персистентные через
  state.json (`export_state`/`import_state`).

Результаты: **9/9 новых тестов V4 PASS** (негативная валидация: **9/9

## 4. Проблема №1 — как определяется хронологический порядок

**Авторитетное время закрытия — столбец `exit_time`** (ТЗ п.1–2).

- Новые строки (v4): `exit_time` = `pos.close_requested_at` — время
  ЗАПРОСА закрытия (триггер SL/TP / отправка SELL), одна из самых
  ранних и самых достоверных отметок фактического закрытия, доступная
  БЕЗ изменения execution.py (там нет терминального таймстампа; его
  добавление — вне рамок этапа). Значение фиксируется ОДИН раз при
  записи строки и recovery-обновлениями не меняется — стабильность
  набора сделок. Для закрытий без своей заявки (B3) и позиций без
  `close_requested_at` — момент записи строки (единственная доступная
  оценка; это не «скрытая подстановка при пересчёте», а честная
  фиксация момента, когда система узнала о закрытии).
- Исторические строки (≤v3): `exit_time` = момент записи строки —
  обрабатываются по тому же правилу «exit_time, если достоверен»
  (детерминированно; отличие от фактического времени закрытия для них
  ограничено и задокументировано в §9).

**Fallback-цепочка (ТЗ п.3) — только поля самой строки, по убыванию
близости к моменту закрытия:**
`exit_time → timestamp_utc (время запроса закрытия) → order_send_time
(отправка SELL) → signal_time`. Значение разбирается как ISO-время
(naive трактуется как UTC); пустое/некорректное — переходит к
следующему полю.

**Полностью неизвестное время** — фиксированный якорь
`datetime(1, 1, 1, UTC)`: строка сортируется первой. Это НЕ текущее
системное время (запрет ТЗ п.3/V4-D): повторный запуск не меняет
результат ни на микросекунду.

**Tie-breaker (ТЗ п.4)** — `trade_id` (лексикографически), затем индекс
строки в файле: полный детерминированный порядок даже при равных
метках и даже при дублирующихся trade_id.

**Свойства пересчёта** (`_recompute_cumulative`, `recompute_cumulative_chronological`):
- строки файла НЕ переставляются и их поля не меняются — обновляется
  ТОЛЬКО столбец `cumulative_net_pnl_rub` (ТЗ п.6);
- `net_pnl_rub` не изменяется, кроме подтверждённых фактических данных
  по логике v3 (ТЗ п.7);
- строки с пустым/нечисловым net (PRICE_UNKNOWN) не меняются и в сумму
  не входят (сохранено из v3);
- позднее изменение net старой сделки пересчитывает cumulative всех
  последующих сделок именно в хронологии (ТЗ п.8);
- результат детерминирован: одинаковый набор сделок всегда даёт
  одинаковые cumulative (ТЗ п.9);
- исторические timestamps не меняются ради сортировки (ТЗ п.10).

**Когда выполняется канонизация:**
1. после каждой успешной записи строки (`log_trade`) — журнал
   каноничен после любой записи; если хронология совпадает с порядком
   файла (штатный случай) — файл НЕ переписывается (идемпотентность);
2. при recovery-обновлении строки (`update_trade_row`, v3-механизм) —
   теперь тоже хронологически.

Выбор точки (после записи, а не каждый цикл) — сохранение
байт-идемпотентности существующих сценариев v3 (тест M: ручная
дополнительная строка + отказ обновления не должны менять файл).

## 5. Проблема №2 — как хранятся незавершённые recovery-задачи

**Архитектура: персистентный архив снимков закрытых сделок в
`ExecutionMonitor`.**

- `ExecutionMonitor.pending_csv_recoveries: List[dict]` — каждая задача:
  `{"version", "trade_id", "figi", "ticker", "reason",
  "position": pos.to_dict()}` — ПОЛНЫЙ JSON-безопасный снимок позиции
  на момент архивации (все поля `TrackedPosition`, включая
  `close_orders` — per-order cursor'ы, `close_order_request_id`,
  `close_order_id`, `trade_id`, `lot_size`, `entry_price`,
  `price_before_order`, `close_price_before_order`,
  `entry_actual_commission`, `exit_price_confirmed`).
  Достаточная информация для повторного получения фактического статуса
  СВОЕЙ SELL-заявки (ТЗ п.4): обе ссылки (клиентский UUID —
  `close_order_request_id`, биржевой ID — `close_order_id`) и
  замороженный терминальный cursor.
- **Архивация** — `archive_pending_csv_recovery(pos)`, вызывается в
  `register()` и `register_recovery()` РЯДОМ с существующим
  `_archive_closed_entry_order` ПЕРЕД заменой `positions[figi]`.
  Условие (консервативное, только по данным позиции): CLOSED + logged
  (CSV-строка записана) + стабильный trade_id + ссылка на СВОЮ
  close-заявку. Не архивируются: незалогированные закрытия (строки ещё
  нет — восстанавливать нечего) и B3-внешние закрытия без своей SELL
  (опрашивать нечего). Дедуп по trade_id.
- **НЕ единственный источник** (ТЗ п.3): recovery-цикл в
  `process_closing` теперь ДВУХчастевый — (а) прежний проход по
  живым `monitor.positions` (CLOSED+logged), (б) новый проход по
  `pending_csv_recoveries`. Архив не зависит от текущего активного
  объекта `positions[figi]`.
- **Персистентность**: `export_state()` добавляет
  `"pending_csv_recoveries"` в state.json; `import_state()` восстанавливает
  с валидацией. Runtime-only ключи записей (префикс `_`) в state.json не
  попадают.

### Изменение state.json — миграция и совместимость

Расширение ДОБАВЛЯЕТ ОДИН ключ верхнего уровня (`pending_csv_recoveries`),
формат существующих полей (positions/closed_entry_order_ids/risk) не
меняется:
- **Прямая совместимость**: старые версии при чтении нового state.json
  игнорируют неизвестный ключ (их `import_state` читает только
  известные поля) — rollback безопасен.
- **Обратная совместимость**: старый state.json без ключа → пустой
  список (поведение v3) — тест V4-G и тест F v3 проходят.
- **Повреждённые/неполные данные**: запись не-dict, без снимка
  позиции, с невосстановимым снимком (`TrackedPosition.from_dict`
  падает) или без trade_id — отбрасывается ЦЕЛИКОМ с журналом ERROR
  (fail-closed по записи, без падения процесса); остальные записи
  восстанавливаются. `pending_csv_recoveries` не-list → восстановление
  пропущено с журналом.
- Ручное редактирование state.json не выполнялось и не требуется.

### Почему execution.py потребовалось изменить

ТЗ допускает изменение execution.py «если это не требуется непосредственно
для сохранения идентичности старых recovery-задач» — именно этот случай:
идентичность старой сделки (снимок + ссылки на СВОЮ заявку + cursor)
должна переживать замену объекта позиции, что возможно только внутри
монитора, владеющего `positions`. Изменения минимальны: одно поле,
один метод, два вызова-хука, экспорт/импорт. Механика B2
(`apply_close_execution`, per-order cursor, resolve_closing) —
БАЙТ-ИДЕНТИЧНА v3 (проверено диффом).

## 6. Как работает восстановление после перезапуска

1. Сделка закрыта, CSV-строка записана (logged=True), цена/комиссия
   частично неизвестны.
2. `register()`/`register_recovery()` регистрирует новую позицию того же
   FIGI → ПЕРЕД заменой закрытая позиция снимается в архив
   (`pos.to_dict()`).
3. Каждый цикл `process_closing` (и при работе, и после перезапуска):
   снимок восстанавливается как ОТСОЕДИНЁННЫЙ объект
   (`TrackedPosition.from_dict(rec["position"])`) — в
   `monitor.positions` НЕ возвращается; `_recover_late_csv_metadata`
   выполняется по снимку с той же семантикой v3 (шаги 1–6: поиск строки
   по trade_id → проверка необходимости опроса → опрос СВОЕЙ заявки →
   сверка с замороженным cursor'ом → безопасное обогащение → атомарное
   обновление строки).
4. Снимок задачи синхронизируется с рабочим состоянием после каждого
   прохода (`rec["position"] = task_pos.to_dict()`) — обогащённый
   cursor персистентен, и конфликт ЛЮБОГО позднего отчёта с уже
   подтверждённым значением обнаружится и после перезапуска (та же
   защита, что у живых позиций).
5. Задача удаляется ТОЛЬКО при завершённом восстановлении: в строке
   подтверждены И цена, И фактическая комиссия (критерий совпадает с
   самоограничением опроса v3) + событие `CSV_RECOVERY_TASK_COMPLETED`
   (ТЗ п.10). Новая позиция по тому же FIGI удаление задачи не
   инициирует (ТЗ п.12). Невосстановимый снимок — единственный
   fail-closed-случай принудительного удаления (событие
   `CSV_RECOVERY_TASK_DROPPED`, никаких изменений CSV/учёта).
6. Идемпотентность (ТЗ п.9): повторный опрос с теми же данными →
   `update_trade_row` возвращает "unchanged" (файл байт-в-байт);
   после перезапуска восстановление повторяется корректно (V4-G).

## 7. Как исключается перепутывание сделок с одинаковым FIGI

- **Идентичность через trade_id** (ТЗ п.1): задача несёт СВОЙ
  trade_id; обновляется СУЩЕСТВУЮЩАЯ строка по нему; missing/ambiguous
  → отказ (fail-closed v3 сохранён).
- **Своя заявка** (ТЗ п.5): опрос выполняется по ссылкам ИЗ СНИМКА
  СТАРОЙ сделки (`close_order_id` — биржевой ID → EXCHANGE; иначе
  `close_order_request_id` — клиентский UUID → REQUEST). Заявка новой
  позиции не существует для recovery (её cursor'ов в снимке нет).
  Тест V4-E дополнительно проверяет `client.state_calls`: только
  `sell-e1` (старая заявка).
- **Различие идентификаторов** (ТЗ п.6): `trade_id` (стабильный

## 9. Известные ограничения (без маскировки)

1. **Мультиордерные закрытия** — ограничение v3 сохранено: recovery
   обрабатывает close-заявку, на которую указывают ссылки позиции
   (последняя заявка закрытия — она же в столбце order_id CSV-строки).
2. **CLOSED+НЕlogged позиции, вытесненные register()** — строки CSV ещё
   нет, восстанавливать нечего; архивация таких позиций не выполняется
   (создание отсутствующей строки — новая функциональность, вне рамок
   ТЗ). Ограничение унаследовано от v3 (§7.2).
3. **Позиции без trade_id** — не архивируются и не восстанавливаются
   (fail-closed, как в v3).
4. **B3-внешние закрытия** — без своей SELL-заявки опрос невозможен;
   строка остаётся PRICE_UNKNOWN по дизайну; B3 не менялся.
5. **Задачи, для которых брокер никогда не передаёт комиссию** —
   остаются в архиве и опрашиваются каждый цикл (самоограничение:
   опрос только строк с пустыми полями; семантика идентична v3 §7.5
   для живых позиций). Расширение политики ретраев — вне рамок.
6. **Полные строки не опрашиваются** — если цена И фактическая
   комиссия уже в строке, противоречивый поздний отчёт не проверяется
   (нет опроса → нет изменений → fail-closed по существу); компромисс
   v3 §7.6 сохранён.
7. **exit_time для исторических строк (≤v3)** — момент записи строки;
   точность хронологии для них ограничена (столбец не пересчитывается
   задним числом — «не менять исторические timestamps», ТЗ п.10).
   Для новых строк exit_time = время запроса закрытия.
8. **exit_time vs фактическое исполнение** — `close_requested_at` чуть
   раньше фактического исполнения SELL (время запроса, а не сделки);
   терминальный таймстамп в execution.py не добавлялся (вне рамок:
   execution.py менялся только для идентичности recovery-задач).
   Для хронологического ПОРЯДКА это несущественно: относительный
   порядок запросов закрытия соответствует порядку их исполнения.
9. **Канонизация при записи** — журнал каноничен после каждой записи;
   файл, оставшийся неканоничным после сбоя записи, канонизируется при
   следующей успешной записи. Между сбоями возможен старый порядок
   cumulative (атомарность гарантирует целостность, но не каноничность).
10. **Неисправленные сторонние наблюдения** (зафиксированы, не
    исправлялись без согласования): семантика `pos.executed_lots`
    при мультиордерных закрытиях (v3 §7.1); отсутствие
    терминального таймстампа в cursor'е (см. п.8).

Главный принцип соблюдён: одна фактическая сделка сохраняет свою

финансовый учёт (своя строка CSV, свой вклад в хронологический
cumulative) независимо от порядка закрытия других сделок, появления
новой позиции по тому же FIGI и перезапуска программы.
