## 1. Статус

Тест входит в 12 обязательных P0-тестов ТЗ (FIX-2). После корректного
обновления заглушек (FIX-2) тест ВЫПОЛНЯЕТСЯ и проходит 8 из 9 своих
утверждений; последнее утверждение (`rec["status"] == "CANCELLED" and
rec["executed_lots"] == 5`, строка 470 корневого файла) фиксирует
семантический конфликт production-кода кандидата. По критерию ТЗ §4
тест получает статус **NOT VERIFIED (блокирован производственным
контрактом)**; production-код НЕ исправлялся (ТЗ FIX-2 п.7: реальная
ошибка production-кода описывается отдельно и требует отдельного решения).

## 2. Точная цепочка событий (диагностика, только stub)

Воспроизведение фаз теста с печатью записей реестра (order_ledger.jsonl):

```
STATUS=INTENT        exec=None price=None comm=None
STATUS=PARTIALLYFILL exec=2    price=None comm=None
STATUS=CANCELLED     exec=2    price=0.0  comm=None
  REASON=позиция зарегистрирована; RECOVERY: no_price
STATUS=UNCERTAIN     exec=5    price=0.0  comm=None
  REASON=позднее исполнение применено к позиции (+3 лот., итого 5);
         identity/metadata contradiction of repeat report: avg_exec_price 0.0->100.0
```

## 3. Корневая причина (по коду)

1. Фаза 1: отчёт CANCELLED с частичным исполнением 2 лота БЕЗ цены
   (`price_units=0` → `ExecutionMonitor._extract_price` возвращает **0.0**,
   а не None). `main.register_executed_buy` вызывает
   `ledger.record_status(..., avg_exec_price=exec_price ...)` БЕЗ
   нормализации: в реестр записывается `avg_exec_price = 0.0`.
2. FIX-1 кандидата в `order_ledger.OrderLedger.append` (строки 217-251):
   повторный отчёт УЖЕ ТЕРМИНАЛЬНОЙ заявки с изменившейся ценой/комиссией
   трактуется как «identity/metadata contradiction» → запись переводится в
   UNCERTAIN (fail-closed), прежнее значение 0.0 сохраняется.
3. Фаза 4: поздний отчёт той же заявки (2→5 лот.) несёт РЕАЛЬНУЮ
   кумулятивную цену 100.0 (500 / (5×1)). `apply_late_entry_lots`
   корректно применяет +3 лота к OPEN-позиции (все position-утверждения
   теста проходят), но `ledger.record_status(CANCELLED, executed=5,
   avg_exec_price=100.0)` конфликту­ет с зафиксированным «подтверждённым»
   0.0 → реестр: UNCERTAIN вместо CANCELLED.

## 4. Классификация

Это НЕ дефект заглушки (заглушки обновлены, тест выполняется) и НЕ
устаревшая семантика теста сама по себе: тест — регрессионный guard партий
P0-2/3/4, и его поведение изменилось ПОСЛЕ добавления кандидатом FIX-1
(metadata-guard реестра) БЕЗ нормализации нулевой цены в BUY-пути.

Несогласованность внутри кандидата:
* B2/SELL-путь (`execution.apply_close_execution`, строки 805-806): цена
  сохраняется в cursor ТОЛЬКО при `execution_price > 0` — нулевая цена
  НЕ записывается как «подтверждённая»;
* BUY-путь (`main.register_executed_buy` → `ledger.record_status`): нулевая
  цена записывается в реестр как значение → блокирует легитимное позднее
  уточнение цены терминальной BUY-заявки (fail-closed UNCERTAIN).

Отдельно отмечено: для КОМИССИИ кандидат зафиксировал противоположную
семантику (FIX-3: «0.0 — достоверное значение», потому что нулевая комиссия
реальна). Для ЦЕНЫ ноль реальным значением не является (везде валидность —
`price > 0`), поэтому запись 0.0 в реестр как «подтверждённой цены» —
несогласованное поведение.

## 5. Риск (если оставить как есть)

Любая BUY-заявка, чей первый терминальный отчёт содержал исполнение без
цены (executed_order_price=0), получает в реестре «подтверждённую» цену 0.0;
последующее легитимное уточнение цены брокером → UNCERTAIN-запись,
блокировка новых BUY по FIGI до подтверждённой сверка портфеля
(разрешается reconcile/повторным терминальным отчётом после сверки —
механизм P0-5). Учёт лотов не искажается (проверено тестом: quantity=5,
applied=5 — позиционные утверждения проходят). Риск — операционный шум и
лишние блокировки, НЕ двойной учёт.

## 6. Варианты исправления (ДЛЯ ОТДЕЛЬНОГО ТЗ, здесь НЕ выполнялись)

Вариант-1 (минимальный, согласован с B2): нормализация в точке записи —
`avg_exec_price=None if (exec_price is None or exec_price <= 0)` в вызовах
`ledger.record_status`/`record_sent` BUY-пути.
Вариант-2: в metadata-guard `OrderLedger.append` трактовать
`avg_exec_price <= 0` как «значения нет» (симметрично None) — меняет
общий модуль реестра, требует отдельной проверки B2/SELL-путей.
