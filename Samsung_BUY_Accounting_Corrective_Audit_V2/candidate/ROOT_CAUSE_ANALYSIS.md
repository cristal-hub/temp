# ROOT CAUSE ANALYSIS — инцидент WUSH (BUY 495 лотов)

Проект: Tsclp_v2.1_volatile_Samsung. Каталог: `temp/samsung_BUY_accounting_audit_v1/`.
Метод: аудит кода кандидата (Samsung `051b10f` + B2 v1–v7) + синтетические
воспроизводимые тесты. Реальные логи инцидента недоступны.

```
RESEARCH ONLY
NO LIVE ORDERS
OOS SEALED / H4 EXECUTION NOT AUTHORIZED
```

## 0. Факты инцидента (приняты как исходные, не перепроверялись)

- Инструмент WUSH; BUY на 495 лотов.
- Брокер подтвердил исполнение (источник: подтверждение брокера, вне кода).
- Локальная активная позиция после этого отсутствовала.
- Позднее при сверке появилась RECOVERY-позиция.
- Точная первопричина не установлена (состояние на момент аудита).

## 1. Кандидаты первопричины (по коду кандидата, с уровнями доказанности)

Уровни: **[КОД]** — доказано чтением кода кандидата (файл/функция/условия);
**[СИНТЕТИЧЕСКИЙ ТЕСТ]** — воспроизведено тестом на заглушках
(`test_buy_accounting_audit.py`); **[ГИПОТЕЗА]** — правдоподобно, но не
проверяемо без реальных артефактов.

### RC-1. Крах/останов процесса после `record_sent` и до регистрации позиции [КОД]

Окно: `trading_cycle` → `post_market_order` OK → `ledger.record_sent(FILL, 495)`
записан → процесс упал до `register_executed_buy`/`_save_state_checked`.
Ledger считает исполнение (FILL 495), state.json не содержит позиции.

- В кандидате окно закрыто: `startup_recovery` (проход 1.5) доводит терминальные
  FILL-заявки без маркера «позиция зарегистрирована» до регистрации через
  единую точку (main.py, комментарий «Исправление (дефект №1 — восстановление
  после краха между record_sent() и регистрацией позиции)»).
- При цене, недоступной из реестра (`avg_exec_price=None`), регистрация идёт в
  RECOVERY — согласуется с фактом появления RECOVERY-позиции после инцидента.
- [СИНТЕТИЧЕСКИЙ ТЕСТ] `test_wush_synthetic_buy495_recovery`: ровно этот
  сценарий — BUY 495, ledger сохранён, state нет → ровно одна RECOVERY-позиция
  495; повторные сверки и поздний отчёт не дублируют и не удваивают.
- Оценка: если инцидент произошёл на коде БЕЗ прохода 1.5 (старая версия до
  «дефекта №1»), потеря регистрации и поздняя адопция как RECOVERY — прямое
  следствие. [ГИПОТЕЗА] — требуется версия кода на момент инцидента.

### RC-2. Крах/потеря ответа между принятием заявки брокером и `record_sent` [КОД]

Окно: `post_market_order` принят брокером → ответ потерян/процесс упал → в
реестре только INTENT (или ничего, если упал до record_intent).

- INTENT-путь: `record_intent` до сетевого вызова (fail-closed) → при
  перезапуске заявка в `open_orders()` → poll/startup запрашивает статус по
  REQUEST → исполнение регистрируется (RECOVERY при неполных данных). [КОД]
- Крах ДО `record_intent`: реестр не знает заявку; АКТИВНАЯ заявка брокера
  обнаруживается startup-ом (UNCERTAIN), но ТЕРМИНАЛЬНАЯ FILL-заявка в списке
  активных не значится — позиция обнаруживается только адопцией
  `reconcile`/startup pass 3 как RECOVERY (без entry_order_id/цены). [КОД] —
  это единственное окно, в котором BUY-заявка не оставляет в реестре следа;
  оно существует и в кандидате.
- [СИНТЕТИЧЕСКИЙ ТЕСТ] частично покрыт (адопция без реестра — ТЗ-15; «заявка
  без записи реестра» — startup pass 2). Прямой тест «крах до INTENT»
  эквивалентен отсутствию записи в реестре; покрыт через адопцию.
- Оценка: правдоподобный кандидат первопричины, если в момент инцидента
  процесс был убит до INTENT (например, OOM/kill на старте цикла). [ГИПОТЕЗА]

### RC-3. Появление RECOVERY-позже — штатное поведение, а не дефект [КОД]

Появление RECOVERY-позиции «при сверке» — штатный механизм адопции
(`reconcile` / `startup_recovery` pass 3: «позиция брокера без локального
учёта — зарегистрирована как RECOVERY») или штатная регистрация исполненного
BUY с неполными данными (цена неизвестна → RECOVERY, `recovery_source=no_price`).

- [КОД] В обоих путях RECOVERY: автозакрытие запрещено, новые BUY по FIGI
  заблокированы, промоция после восстановления цены входа.
- Оценка: сам факт RECOVERY не является ошибкой — он является СЛЕДСТВИЕМ
  отсутствия локальной регистрации на момент сверки. Первопричина — в
  RC-1/RC-2 (или исторической версии кода).

### RC-4. Двойное/частичное применение, «потерявшее» позицию [КОД — опровергнуто для кандидата]

Гипотеза «позиция была зарегистрирована и затем потеряна учётной логикой»:

- Активная запись по FIGI перезаписывается только через guard-и (`register`
  отказывает при активной позиции; CLOSED-записи архивируются в
  `closed_entry_order_ids`, «воскрешение» запрещено). [КОД]
- Перезапуск возвращает позиции из state.json; при повреждении state —
  `_load_state=False` + запрет новых входов, позиции не теряются молча. [КОД]
- [СИНТЕТИЧЕСКИЙ ТЕСТ] ТЗ-2/12/14/15/18 — потеря активной записи из-за
  повторов/чужих заявок/сверок не воспроизводится.
- Оценка: для кандидата гипотеза опровергнута на уровне кода и тестов;
  для исторической версии кода — [ГИПОТЕЗА].

### RC-5. Расхождение state ↔ ledger, из-за которого восстановление пропустило заявку [КОД — закрыто в кандидате]

Если бы ledger подтверждал «позиция зарегистрирована» при несохранённом state,
pass 1.5 пропустил бы заявку по reason-маркеру — подтверждённое исполнение
потерялось бы. В кандидате подтверждение пишется ТОЛЬКО после успешного
`_save_state_checked` (AUDIT_REPORT.md §1.2). [КОД]

- [СИНТЕТИЧЕСКИЙ ТЕСТ] ТЗ-16 (state-ошибка → маркера нет), ТЗ-5/6/18.
- Оценка: закрыто в кандидате; в исторической версии — [ГИПОТЕЗА].

### RC-6. Сбой записи/повреждение реестра или state в момент инцидента [ГИПОТЕЗА]

Повреждённая строка `order_ledger.jsonl` → `_mark_unreliable` (новые BUY
запрещены, журнал не восстанавливается автоматически) — учёт заявок инцидента
мог быть утрачен при ручном «восстановлении» файла вне кода. Код не удаляет и
не переписывает журнал; но внешние манипуляции (архивы RESET_* в репозитории
свидетельствуют о ручных сбросах состояния 2026-11-21/23) могли удалить записи.
[ГИПОТЕЗА] — требует журнала операций на момент инцидента.

## 2. Итог по первопричине

**Первопричина инцидента WUSH НЕ подтверждена.** Наиболее согласованные с
фактами (подтверждённый BUY, отсутствие позиции, поздняя RECOVERY) кандидаты:

1. RC-1/RC-5 — крах в окне «исполнение подтверждено → позиция не сохранена»
   на коде, где восстановительное окно ещё не было закрыто (проход 1.5
   появился как «Исправление (дефект №1)» ПОЗЖЕ инцидента). Согласуется с
   хронологией репозитория (фиксы BUY-регистрации датируются после инцидента).
2. RC-2 (крах до INTENT) — след в реестре отсутствует вовсе; позиция
   обнаруживается только адопцией.

Оба кандидата объясняют позднюю RECOVERY-позицию как штатную адопцию (RC-3).

**Важно: не заявляется, что инцидент «решён».** Синтетический тест
(`test_wush_synthetic_buy495_recovery`) доказывает только то, что КАНДИДАТ
воспроизводит сценарий без потери и без дублей — он НЕ доказывает, что
первопричина исторического инцидента именно эта.

## 3. Какие дополнительные реальные данные требуются для окончательного подтверждения

1. **`order_ledger.jsonl` на момент инцидента** (полный, до/после): наличие
   INTENT/SENT/FILL-записи заявки WUSH, её `order_request_id`,
   `avg_exec_price`, таймстампы — различает RC-1 (FILL есть) и RC-2 (записи нет).
2. **`state.json` на момент инцидента** (до/после перезапуска): была ли
   позиция сохранена; `closed_entry_order_ids`; версии полей.
3. **`research_events.jsonl` инцидента**: `SIGNAL`/`ORDER_INTENT`/
   `BUY_UNKNOWN`/`STATE_SAVE_FAILED`/`POSITION_OPENED`/`POSITION_RECOVERED` с
   таймстампами — точное место разрыва.
4. **Логи процесса** (logging-файл) вокруг перезапуска: строки `[startup]`,
   `[register]`, `[reconcile]` — какой проход что сделал.
5. **Версия кода** (git-коммит/дифф), работавшая в момент инцидента —
   определяет, были ли уже закрыты окна RC-1/RC-5.
6. **Подтверждение брокера**: отчёт заявки (order_id, executed_order_price,
   комиссия, время исполнения) — сверка с реестром.
7. **Обстоятельства перезапуска**: причина падения процесса (kill/OOM/
   обновление), время между падением и перезапуском.

При наличии 1–4 первопричина подтверждается или исключается детерминированно:
запись FILL в реестре + отсутствие маркера «позиция зарегистрирована» +
RECOVERY при свере = RC-1; отсутствие всех записей заявки = RC-2; наличие
маркера и пропущенная позиция = RC-5 (в кандидате закрыт).
