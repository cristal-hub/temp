## 1. Краткий результат

Устранён дефект восстановления метаданных повторного терминального отчёта:
`ExecutionMonitor.apply_close_execution()` (execution.py) при повторном
терминальном отчёте по уже учтённой SELL-заявке возвращал False **до**
обновления `rec["avg_exec_price"]`, `rec["commission"]`,
`pos.execution_price`, `pos.actual_commission`. Это корректно защищало от
повторного списания количества, но теряло фактически предоставленные брокером
цену/комиссию, если при первой обработке они отсутствовали (None), а при
последующем опросе брокер их уже передал.

Реализовано **безопасное обогащение** уже учтённого терминального отчёта:
новые подтверждённые метаданные сохраняются в per-order cursor и
синхронизируются в поля позиции; повторное применение лотов по-прежнему
невозможно; противоречие двух достоверных значений — fail-closed.

Изменён **только execution.py** (минимальное точечное изменение, как разрешено
ТЗ — дефект находится непосредственно в этом методе). main.py, B3, стратегия и
все прочие механизмы — без изменений.

Результаты: **8/8 новых тестов PASS, 20/20 существующих B2-тестов PASS,
полный pytest 74 failed / 594 passed / 1 error** — FAILED-набор побайтно
идентичен baseline (74 failed / 586 passed / 1 error), новых ошибок нет;

## 3. Что было исправлено (детально)

### 3.1 Дефект

Точка дефекта — повторный путь `apply_close_execution()` (execution.py):
после проверки «cumulative > учтённого терминального» (защита от роста) метод
сразу логировал «игнорируется» и возвращал False. Отчёт мог содержать НОВЫЕ
достоверные метаданные (цену исполнения и/или фактическую комиссию),
отсутствовавшие при первой обработке, — они терялись: cursor и поля позиции
оставались с None, CSV/учёт оставались без фактически доступных данных.

Пример из ТЗ: первый отчёт CANCELLED, cumulative=3, applied=3, price=110,
commission=None; повторный достоверный отчёт CANCELLED, cumulative=3,
price=110, commission=1.5. Ожидаемо (и теперь фактически): applied остаётся 3,
quantity повторно не уменьшается, close_applications не растёт, комиссия
обновляется до 1.5, `pos.actual_commission` становится 1.5, статус позиции не
меняется из-за безопасного повтора. Аналогично восстанавливается цена.

### 3.2 Реализация (execution.py, только повторная терминальная ветка)

1. Добавлен модульный хелпер `_report_value_conflict(saved, reported)`:
   True ТОЛЬКО когда ОБА значения достоверны (не None) и различаются сверх
   денежного допуска 1e-9; непарсируемое «достоверное» значение —
   консервативно конфликт (fail-closed). Семантика зеркальна
   `main._confirmed_value_conflicts` (проверка идентичности повторов В2) —
   оба уровня защиты согласованы.
2. В повторной ветке, ПОСЛЕ сохранённой проверки роста cumulative
   (`cumulative > previous` → UNCERTAIN, без изменений):
   - проверка конфликта цены и комиссии; при конфликте — UNCERTAIN,
     logging.error («противоречит учтённому ... fail-closed»), return False,
     БЕЗ перезаписи исходных значений и БЕЗ повторного применения;
   - безопасное обогащение: `avg_exec_price`/`commission` записываются в
     cursor ТОЛЬКО если сохранённое значение None и новое значение
     достоверно (цена — ещё и > 0, как в штатном пути);
   - уже известное значение НЕ перезаписывается другим автоматически;
   - отсутствие значения в новом отчёте (None) НЕ затирает сохранённое и
     НЕ является противоречием;
   - синхронизация `pos.execution_price`, `pos.actual_commission` и
     `pos.exit_price_confirmed` с (обогащённым) cursor'ом;
     `exit_price_confirmed` следует неизменному инварианту ТЗ-5
     («цена подтверждена ТОЛЬКО из отчёта реального исполненного
     close-ордера») — при восстановлении цены False → True, при сохранённой
     цене — не понижается;
   - состояние позиции НЕ меняется; applied_lots / confirmed_executed_lots /
     pos.quantity / close_applications / legacy-ссылки не изменяются;
   - защита от роста cumulative после терминального статуса СОХРАНЕНА
     (проверка стоит ВЫШЕ блока обогащения и выполняется первой);
   - журнал: при обогащении — «восстановлены метаданные брокера: ...», при
     чистом повторе — прежнее сообщение (не ломает существующие тесты).

### 3.3 Почему потребовалось изменение execution.py

Дефект находится непосредственно в `apply_close_execution()`: данные терялись
в момент раннего `return False` повторной ветки — до записи метаданных в
cursor. Компенсировать это в main.py было бы обходом уровня выше с
дублированием логики cursor'а (риск расхождения двух «истин» о цене/комиссии)
и правкой main.py — недопустимым расширением объёма. ТЗ прямо разрешает и
предписывает точечное изменение execution.py. Другие модули не требовались:
`order_ledger.py`, `main.py`, стратегия, риск, скринер, B3 — не изменены.

### 3.4 Идемпотентность и согласованность с B2 main.py

- Повтор возвращает False (контракт сохранён) → B2-проверка идентичности в
  main.py (статус/лоты/цена/комиссия с учётом отсутствующих optional-значений
  и нормализации статусов) выполняется КАК РАНЬШЕ на каждом повторе;
  обогащённый cursor согласован с отчётом (нет ложных конфликтов).
- Обогащение идемпотентно: значение записывается один раз (когда saved=None);
  последующие идентичные повторы не меняют ничего.
- Синхронизация pos-полей идемпотентна (чтение cursor'а).
- Противоречие детектируется ДВУМЯ независимыми уровнями (execution.py и
  main.py) с одинаковой семантикой — итог одинаково fail-closed (UNCERTAIN,
  `client.uncertain_state=True`, событие `SELL_CLOSE_REPORT_CONTRADICTION` от
  main.py, лог execution.py), повторного применения нет.

### 3.5 Метаданные — только фактические данные брокера

Обогащение принимает ТОЛЬКО значения, переданные вызывающим кодом из
брокерского отчёта (`ExecutionMonitor._extract_commission(state)` /
`_extract_price(state, ...)`) или из достоверной записи реестра. Расчётная
(модельная) комиссия и приблизительная цена не подставляются — это
гарантировано существующим кодом main.py (v2.3.4-stage2) и не изменялось.

## 8. Известные проблемы / особенности

1. **CSV-строка первой обработки не переписывается.** Если CSV-строка была
   записана при первой обработке (без комиссии), безопасный повтор с
   восстановленной комиссией НЕ переписывает уже записанную CSV-строку
   (позиция уже logged). Требованием ТЗ перезапись CSV не предусмотрена
   (проверки: «CSV не дублируются»); восстановленные данные доступны в
   cursor'е и полях позиции для последующего учёта и диагностики. Изменение
   механики перезаписи CSV потребовало бы правки process_closing — вне объёма
   разрешённого изменения.
2. **Pre-existing collection error** корневого test_execution.py (дерево
   Samsung, `ROOT = parent.parent`) — идентичен в baseline и final, к
   исправлению не относится.
3. **74 pre-existing failed** полного прогона — зафиксированы как baseline
   предыдущих поставок, НЕ чинились (прямое ограничение).
4. Push в GitHub из песочницы невозможен (нет учётных данных): результат
   закоммичен локально в ветке `temp-merge-candidate-v2` (на базе temp/main
   @ de5e945, предыдущая папка samsung_merge_candidate/ сохранена в дереве);
   пакет продублирован в download/ для загрузки пользователем.
