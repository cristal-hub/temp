# UNVERIFIED_AND_RISKS.md — непроверенное и риски (ТЗ V3, честная фиксация)

## 1. NOT VERIFIED

### 1.1. Контракт SDK t-tech-investments в живом окружении
Пакет `t-tech-investments==1.51.0` (requirements.txt) — приватный, в аудиторской среде
недоступен из PyPI («Could not find a version…»). Все прогоны выполнены на conftest-заглушках
(штатный CI-режим проекта, идемпотентных и предназначенных именно для этого). Следствия:
* соответствие заглушек реальному protobuf-контракту SDK (поля OrderState, enum-коды,
  Quotation) проверено только по коду и истории проекта, не «вживую»;
* subprocess-тесты persistence теперь проходят на заглушках; в окружении пользователя
  с реальным SDK они пройдут через ту же ветку (`_install_stubs()` — no-op при наличии SDK).
**Риск:** низкий; поведение в живом окружении рекомендуется перепроверить одним прогоном
`run_tests.ps1` у пользователя.

### 1.2. Поведение на реальном/sandbox брокере
Вне RESEARCH-мандата (запрет §1). Исправления V3 проверены только офлайн-сценариями.

### 1.3. Реальные брокерские последовательности «0.0-цена → реальная цена»
Трассировка показывает, что брокер возвращает executed_order_price=0 при lots_executed>0
(воспроизведено в интеграционном тесте, поставляемом самим проектом). Частотность/варианты
таких отчётов на живом API не наблюдались (нет доступа) — исправление верифицировано
синтетическими сценариями всех комбинаций (V3-тесты).

## 2. Риски принятых решений

### 2.1. Смягчение guard'а реестра (V3-2) — ограничено и осознано
Конфликт теперь распознаётся только между двумя ВАЛИДНЫМИ значениями. Сценарий
«подтверждённая цена 100.0 → новый отчёт 0.0» больше не поднимает UNCERTAIN
(0.0 не является ценой). Оценка риска: **низкий** — 0.0-цена не несёт информации,
старое значение сохраняется; настоящие противоречия (100.0→200.0, комиссия 0.0→5.0)
по-прежнему fail-closed (тесты 5 и 11). Альтернатива (оставить 0.0 конфликтом)
воспроизводила бы ложные UNCERTAIN — дефект §5.1 ТЗ.

### 2.2. Синхронизация tests/-копий (V3-T2)
Копии заменены байт-в-байт корневыми версиями. Риск: если какая-то tests/-копия содержала
УНИКАЛЬНОЕ утверждение, отсутствующее в корневой версии, оно могло бы быть утрачено.
Проверено diff-ами (evidence/diffs/copy_drift_*.diff): все различия — подмножество
обновлений корневых версий; уникальных для копий утверждений не обнаружено.

### 2.3. Карантин скриптов и их mock-тестов (ТЗ §2)
58 тестов исключены из полного набора кандидата вместе с system-under-test. Риск
«ослабления покрытия» отсутствует: скрипты не входят в кандидат; их тесты сохранены
в карантине и исполняемы там же.

### 2.4. tests/conftest.py shim (V3-T1)
Корневой conftest импортируется из tests/conftest — при работе под pytest модуль «conftest»
уже загружен, повторного исполнения нет; вне pytest (subprocess) импорт устанавливает
заглушки и импортирует main — что и требуется subprocess-скриптам. Риск конфликта
двойной регистрации autouse-фикстуры отсутствует (фикстура определяется только в
корневом conftest).

## 3. Известные ограничения отчёта

* Статусы получены на mock/stub-инфраструктуре без реального SDK (сравнение baseline/final
  корректно — среда идентична; внешний охват ограничен).
* Исторический «pre-V2» baseline (74f/685p/1e) не воспроизводится в V3-сравнении
  по определению: каноническая база V3 = итог V2 (все принятые исправления V2 включены).
  Точное воспроизведение V2 full FINAL (36f/741p/1e) получено в среде без pandas-ta-classic
  и зафиксировано в TEST_RESULTS.md §2.
* Ранние V2-замечания D-1/D-2 (runtime-файлы в старых пакетах) не применимы к V3-кандидату:
  runtime-файлы отсутствуют (проверено), опасные скрипты карантинизированы.
