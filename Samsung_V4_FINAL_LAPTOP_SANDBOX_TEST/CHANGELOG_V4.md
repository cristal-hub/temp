## V4-1 (P1, ТЗ §2). order_ledger.py — валидация финансовых значений при ПЕРВОЙ записи

* **Дефект:** в V3 проверки `_valid_execution_price()`/`_valid_commission()` выполнялись
  только внутри ветки `if prev is not None:` в `OrderLedger.append()`. Первая запись ордера
  (`prev is None`) обходила их: `avg_exec_price=0.0`/отрицательная/NaN/±Inf и
  отрицательная/NaN/±Inf комиссия попадали в журнал как «подтверждённые».
* **Исправление:** валидация перенесена в цикл копирования полей ДО ветвления по `prev` и
  действует единообразно для всех входных путей (`record_sent`/`record_status`/
  `record_uncertain`/`record_observation`, повторная загрузка и восстановление — все они
  идут через `append()`). Невалидное значение не записывается (нормализуется в None =
  отсутствие достоверного значения); в журнал пишется отсутствие, а не «подтверждённая
  цена/комиссия».
* **Контракт цены:** `None` — легитимное отсутствие; положительная конечная — валидна;
  `0.0`/отрицательная/NaN/±Inf — не записываются как достоверные.
* **Контракт комиссии:** `0.0` — ДОСТОВЕРНЫЙ ноль (семантика BUY V1 FIX-3 сохранена);
  положительная конечная — валидна; отрицательная/NaN/±Inf — не записываются; отсутствие
  (`None`) отличается от нуля; легитимный 0.0 не превращается в пустое значение.
* **Почему безопасно:**
  * повторные записи — guard V3-2/FIX-1 не изменён (работает по raw-значениям `fields`:
    достоверное прежнее значение не затирается, настоящее противоречие двух достоверных
    значений на терминальной заявке — по-прежнему UNCERTAIN/fail-closed);
  * позднее подтверждение обогащает запись `None → валидная цена` как прежде
    (P0-сценарий §3.3 не сломан — профиль P0 70/70, интеграционный тест §5.14 проходит);
  * проверка противоречий между подтверждёнными исполнениями НЕ ослаблена;
  * стратегия/сигналы/фильтры не затронуты; интерфейсы функций не изменены.
* **Тесты:** `test_v4_order_ledger_first_append.py` — 17 тестов (15 обязательных ТЗ §2 +
  2 на единообразие путей `record_sent`/`record_observation`). Каждый проверяет
  возвращаемое значение И фактическое содержимое сохранённого JSONL и/или состояние
  после `load()` (пункт ТЗ «не только возвращаемые значения»).

## V4-2 (ТЗ §7.3). main.py + build_safety.py — Режим A/B и техническая блокировка заявок

* **Дефект (архитектурный):** `trading.flag` в V3 блокировал только НОВЫЕ ВХОДЫ; SL/TP-
  закрытия (`close_position` → SELL, шаг 2 `trading_cycle`) выполнялись ДО проверки
  флага — запуск `main.py` без флага мог отправить SELL по существующим позициям. Для
  laptop-сборки это недопустимо (ТЗ §7.3: «не имитировать безопасность флагом»).
* **Исправление (минимальное):**
  * новый `build_safety.py`: `detect_mode()` (Режим A SAFE_START по умолчанию; Режим B
    = маркер-файл `sandbox_execution.enabled` **И** env `SAMSUNG_V4_BUILD_MODE=
    SANDBOX_EXECUTION`; неизвестное значение env → безопасно SAFE_START), `install_order_guard()`
    подменяет `post_market_order`/`cancel_order` на экземпляре клиента защитными
    функциями, поднимающими `OrderSubmissionDisabledError` ДО любого обращения к сети;
  * `main.py`: 2 добавленные строки в `main()` — `build_safety.assert_sandbox_only()` +
    `build_safety.install_order_guard(client)` — плюс импорт;
  * новый `safe_start.py`: входная точка Режима A (SAFE START / READ-ONLY): зависимости,
    fail-closed валидация конфигурации, само-тест блокировки заявки, read-only проверка
    sandbox API (без создания аккаунта), статус реестра/state, диагностика без секретов;
  * новый `enable_sandbox_execution.py`: интерактивное создание маркера Режима B
    (подтверждение фразой). **GLM не запускал; в поставке неактивирован.**
* **Почему безопасно:**
  * в Режиме A (по умолчанию) ни BUY, ни SELL, ни отмена не могут достигнуть брокера —
    guard перекрывает методы экземпляра, все вызывающие пути (`register_executed_buy`,
    `close_position`, `poll_open_orders`) проходят через них;
  * Режим B не включается ни случайно, ни одним флагом конфигурации: нужны маркер-файл
    (создаётся вручную) + env процесса; LIVE запрещён независимо (уровни: `TinkoffClient.__init__`
    → `SandboxRequiredError`; `config.validate()` → RuntimeError; `assert_sandbox_only()`);
  * в Режиме B поведение production-кода идентично V3 (guard не устанавливается);
  * торговая логика/сигналы/фильтры/риски не затронуты.
* **Тесты:** `test_v4_safety_build.py` — 18 тестов (режимы, fail-closed на неизвестный env,
  блокировка/идемпотентность guard'а, LIVE-блокировка трёх уровней, safe_start pass/fail,
  отсутствие секретов в диагностике, контракт «safe_start не запускает торговый цикл»,
  py_compile всех production-файлов, чистый импорт `main` в subprocess, fail-closed
  конфигурации в чистой среде).

## V4-4 (ТЗ §10, OOS-4). main.py + execution.py — дедупликация терминальных SELL-статусов

* **Дефект:** `_SELL_JOURNAL_TERMINAL_STATUSES` (main.py) дублировала
  `_TERMINAL_SELL_STATUSES` (execution.py) с одинаковым содержимым — будущая правка
  одной копии могла рассогласовать трактовку «терминальности».
* **Исправление:** множество определено ЕДИНОЖДЫ в `execution.py`; `main.py` импортирует
  его под историческим именем (`from execution import _TERMINAL_SELL_STATUSES as
  _SELL_JOURNAL_TERMINAL_STATUSES`). Содержимое и поведение не изменились.
* **Почему безопасно:** чистая дедупликация без изменения значений; все 4 точки
  использования в `main.py` получают тот же набор объектов; направление импорта
  существующее (main уже импортирует execution) — циклов нет.
* **Тесты:** `test_v4_integration_integrity.py::test_sell_block_reason_allows_terminal_close_journal`
  (все 7 членов множества, включая сырые числовые коды) + B2/Stage3-наборы (96+48) green.
